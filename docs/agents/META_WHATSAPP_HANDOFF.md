# Meta WhatsApp Cloud API — owner handoff

**Status:** code is default-disabled and not production-certified. Mock HTTP tests do not establish a Meta sandbox, account, template approval, actual message receipt or production readiness. No credentials, provider settings, messages or charges were created by this work.

## Contract and version

The adapter pins **Graph API v26.0**, and supports an approved **AUTHENTICATION copy-code template** with the OTP mapped to the body parameter and URL button parameter at index 0. The endpoint and component mapping follow [Meta's copy-code authentication template documentation](https://developers.facebook.com/documentation/business-messaging/whatsapp/templates/authentication-templates/copy-code-button-authentication-templates). One-tap and zero-tap variants are not supported. Revalidate API version, template shape and Meta policy before any later activation. Meta's webhook signature is HMAC-SHA256 over the exact request bytes using the app secret, supplied in `X-Hub-Signature-256`; malformed signatures are rejected.

## Separate owner-controlled setup (not performed)

1. Obtain separate approval for provider/account costs and live testing. Establish the Meta business, app and WhatsApp Business account; register and verify the business phone number and arrange the required access permissions.
2. Obtain Meta approval for an authentication **copy-code** template and language, confirming the template's code expiry and policy match the 10-minute challenge. Do not enable a mismatched template.
3. Configure a public HTTPS webhook at `/api/webhooks/meta-whatsapp`, subscribe the WhatsApp Business account to message status events, and configure a dedicated verification token. This endpoint is separate from the generic business messaging webhook. Do not point unrelated business traffic at it: unknown message IDs return 503 for provider retry while the send response may be committing.
4. Set secrets only in the hosting provider's server-side secret store, never in client bundles, source control, chat or logs: `META_WHATSAPP_ACCESS_TOKEN`, `META_WHATSAPP_PHONE_NUMBER_ID`, `META_WHATSAPP_APP_SECRET`, `META_WHATSAPP_VERIFY_TOKEN`, `META_WHATSAPP_GRAPH_VERSION=v26.0`, plus the already documented `AGENT_VERIFICATION_HMAC_SECRET`. Configure `AGENT_VERIFICATION_WHATSAPP_PROVIDER_KEY=meta-whatsapp-cloud`, `AGENT_VERIFICATION_WHATSAPP_SENDER_ID` equal to the phone-number ID, and the approved template name and language. Set `AGENT_VERIFICATION_WHATSAPP_TEMPLATE_APPROVED=true` only after actual approval.
5. Enable `META_WHATSAPP_WEBHOOK_ENABLED`, `META_WHATSAPP_CLOUD_ENABLED`, `MESSAGING_LIVE_ENABLED` and `AGENT_PHONE_VERIFICATION_ENABLED` only under a separate deployment authorization. All are disabled by default. Configure a separately approved SMS adapter if fallback is desired.
6. After authorization, perform a controlled test with a consenting owner-controlled number and reconcile API acceptance, signed status callbacks and OTP confirmation. Acceptance or delivery does not verify ownership, grant agent activation or authorize commissions.

The adapter does not automatically retry unknown responses or fall back after timeouts, rate limits or ambiguous errors. Only specific Meta-confirmed template/recipient rejections are marked safe for a configured SMS fallback. Meta's API has no generic idempotency key for message sending; the application claims a challenge atomically and does not resend an unexpired uncertain challenge. Provider status callbacks are deduplicated and cannot regress a later state. Unmatched callbacks return 503 rather than being silently dropped; monitor them. The database migration must be reviewed and applied through the approved deployment process only, never directly against production during development.
