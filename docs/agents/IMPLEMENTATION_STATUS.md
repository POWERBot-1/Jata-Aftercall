# Agent programme — partial implementation and release blockers

This branch is **not** a complete agent network and is not ready for release. Existing account holders can submit one application; this is not agent activation or a complete registration flow. The phone is unverified and referral tools remain unavailable. No financial policy, provider, payout, production setting or data has been activated or changed.

## Implemented slice

- Existing-account application captures a name, unverified Kenyan mobile number and privacy acknowledgement. One row per user and an audit event are written transactionally. Retries return the existing application, without updating it. Phone uniqueness must be enforced only after trusted verification, not against unverified claims.
- `/agents/dashboard` is an authenticated application-status page; it reads only the signed-in account and does not claim to be the full sales dashboard. Agent-directed login uses a fixed allowlisted destination. `GET` and `POST /api/agents/application` require a session; POST checks origin, validates input and uses the existing process-local limiter. The authenticated admin page lists masked phones and checks the current database role. Admins may reject an application with one of two predefined reasons, except their own; the status transition and audit are atomic and retries do not add audit entries. Approval, verification and activation are not implemented.
- Three additive migrations are included but have not been applied or tested against PostgreSQL. Rollback (only after assessing data loss and dependencies): remove the review-status index and constraint and column, drop `AgentRegistrationThrottle`, then `AgentApplication`, and reconcile Prisma's migration history through the established operational process. Deleting the latter table deletes applications. **Never run this rollback in production without explicit authorization.**
- Applications have no self-service deletion or correction; a retention schedule and operational privacy response path must be established before production use. This slice is not release-ready.

- Agent-only account and application creation is implemented behind `AGENT_SELF_SERVICE_REGISTRATION_ENABLED=true`, default off. It creates a CUSTOMER user without a business and never grants an agent entitlement. Duplicate email and new registration have the same response and no automatic login. The application, user and audit event share a transaction. Website terms are acknowledged; programme terms remain unavailable.
- A database-backed per-network registration limiter stores keyed fingerprints rather than IPs and uses atomic PostgreSQL upserts; the limiter migration has not been applied or integration-tested. The configured Vercel ingress must overwrite forwarding headers. The limiter alone does not constitute comprehensive bot protection. Expired buckets are opportunistically purged; a documented retention job is still needed.

- The commission evaluator is a standalone calculation helper, exercised only by hypothetical test fixtures; it is **not connected to Paystack**, does not independently verify its input, and cannot create or reverse a ledger entry. Rates and policy approval are not configured. Never supply browser data as authoritative input.
- Nairobi daily/monthly closed-period helpers have unit tests. They do not generate reports, run on a scheduler, or deliver messages.

## Discovery

- `User` has CUSTOMER and ADMIN roles; session checks in `lib/auth.ts` verify session version against the database. An agent capability needs a separately enforced server-side profile and status; possessing a link must not grant ADMIN.
- `lib/registration.ts` creates a business during owner registration. It is not an agent-only registration flow. Existing `/r/[code]` and `Referral` are business referrals, tied to an eligible published business. They cannot simply be relabelled as agent referrals.
- `lib/team-access.ts` has a phone verification process that requires an administrator to start it and deliver a code out of band. It is not a self-service public OTP provider. A configured, approved verification and delivery path is required before automatic activation can safely be implemented.
- `lib/messaging/providers.ts` defines adapters, including mock/sandbox. Configuration and authorization of a live provider for these operational messages are unverified. `lib/notification.ts` is business-scoped and its in-memory deduplication is not a durable agent outbox.
- Paystack webhook validation and transaction handling exist in `app/api/paystack/webhook/route.ts` and `lib/paystack.ts`. Commission must be integrated at authoritative persisted transitions, including refunds, rather than trusted from a browser or duplicated payment service. The current `Payment` model has no dedicated verified-at timestamp; a reliable historical timestamp and its provenance must be designed before selecting an effective policy or reporting period.
- No agent report scheduler was identified. A scheduler and durable, idempotent report/outbox processing remain necessary. Existing CI workflows are not a production scheduler.
- `scripts/build.sh` runs migrations when DATABASE_URL is set. Do not use production credentials for local checks; production migrations require owner authorization.

## Required follow-up before release

1. Verify and harden the disabled-by-default agent-only account flow, complete durable abuse/bot controls and programme terms acceptance, and implement phone ownership verification and a review/activation state machine. The existing admin-assisted team verification does not satisfy this requirement.
2. Add reviewed migrations and transactional, unique agent identity, invitation, first-eligible attribution and audited correction models. Enforce server-side ownership, consent, self-referral protection, expiration and replay prevention.
3. Connect verified onboarding and payment events to attribution, agent dashboard and a disabled-by-default versioned commission policy and append-only ledger. Test idempotency, refunds, reconciliation and cross-account isolation against disposable PostgreSQL and Paystack sandbox fixtures.
4. Add durable outbox delivery, retries and accurate provider states, administration and independently scheduled Nairobi-period reports. Configure designated recipients only server-side; prove authorized delivery before claiming it works.
5. Obtain owner decisions on rates, eligible payments, gross/net treatment, refunds, recurring sales, thresholds, legal review, approval and settlement. Do not enable commissions or payouts without approval.
6. Run accessibility, viewport, regression, integration and end-to-end checks and capture real screenshots. Open a release review only when the full acceptance criteria are met.

The existing process-local rate limiter is not a distributed abuse control for serverless instances. Any new public agent endpoint needs an appropriate durable limit or other effective cross-instance protection. The existing registration and business referral paths must remain regression-tested.

### Transactional application notification event foundation

With `AGENT_ADMIN_NOTIFICATION_QUEUE_ENABLED=true` (default off), new existing-account applications and new agent-only registrations record one minimal application-submitted event in the same transaction as the application and audit. A database primary key prevents duplicate events, including concurrent application retries. The event contains only an application identifier, event type and creation time; it does not copy names, phone numbers, nominated destinations, message content or credentials. An event insertion error rolls back the application transaction. Existing applications are not backfilled. ## Default-off notification recipient planning foundation

When both `AGENT_ADMIN_NOTIFICATION_QUEUE_ENABLED` and `AGENT_ADMIN_NOTIFICATION_OUTBOX_PLAN_ENABLED` are exactly `true`, application creation additionally creates one immutable-at-creation recipient plan and a `QUEUED` row per configured administrator in the **same transaction** as the application event. A unique event/recipient key and insert-on-conflict plan prevent replay and concurrent calls from adding or duplicating recipients; later configuration changes do not rewrite an existing plan. The database stores neither phone numbers nor message bodies: recipient identifiers are HMAC-SHA256 of normalized numbers with a server-only key, and the plan stores only its non-secret key version. Keyed identifiers are pseudonymous, not anonymous; protect database access and the HMAC key. This is not an immutable or audit-protected table against arbitrary privileged writes.

The plan flag defaults off, requires the existing event flag, and does not contact any recipient or provider. If explicitly enabled with invalid/missing recipients, a key shorter than 32 bytes or invalid key version, application creation fails closed and its transaction rolls back. A production key must be independently generated from strong randomness and managed securely; length validation does not prove entropy. Rotation, historical-key retention, destination resolution, existing-event backfill and removal/changes to queued recipients need an approved operational design before delivery can be implemented. This foundation cannot claim, send, retry, deduplicate uncertain delivery, dead-letter or recover notifications, and it does not enable WhatsApp or SMS.
