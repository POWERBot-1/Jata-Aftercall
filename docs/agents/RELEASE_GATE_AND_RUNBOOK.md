## Deployment preparation — do not execute without separate authorization

1. **Candidate and gates.** Record the exact commit using `git rev-parse HEAD`, the PR and base SHAs, clean tree, review state, required checks and independent visual evidence. Do not use this document's assessment baseline as a substitute for a final SHA. Stop on a failed or pending required gate.
2. **Migration review.** The PR adds 23 agent migration directories `20261101000000` through `20261123000000`; Prisma applies the checked-in migration history in order. Compare actual deployed migration ledger and checksums to the exact candidate before any action. An intermediate, unpublished version of `20261123000000_agent_notification_replay` was revised before final candidate; any disposable environment that applied that intermediate version is not evidence of a clean upgrade and must be recreated or handled by an explicitly rehearsed recovery plan. Do not alter a deployed migration or delete evidence to force a green status.
3. **Backup and target.** Only after separate authorization, verify a recoverable Neon backup/restore point and test recovery in an isolated environment. Independently verify the intended database target, direct connection and migration guard enrollment according to `docs/MIGRATION_TARGET_GUARD.md`. Do not print connection strings or secrets and do not disable the guard. `scripts/build.sh` invokes the migration gate before Prisma generation when `DATABASE_URL` is set; plan the code and database change together. No production migration has been executed in this assessment.
4. **Configuration.** Names only, no values in logs or chat: `DATABASE_URL`, `DIRECT_URL`, Paystack server configuration, and relevant `AGENT_*`, `META_WHATSAPP_*` and `MESSAGING_WEBHOOK_SECRET` variables. Validate settings in the approved secret store without exposing them. Keep notification queue/plan/claims/worker/callback/replay and live approval flags off; keep referral scheduler and related report activation off until specifically authorized. Existing registration, verification, referral and activation flags also require a release-specific decision. The ledger currently has no connected production accrual writer or payout engine; do not claim that a non-existent payout flag has been tested.
5. **Deployment health and smoke tests.** After authorization and only after gates pass, monitor build/migration result, database connectivity, application health, authentication, applicant/admin/agent paths, authorization boundaries and Paystack webhook error rates. Use approved non-financial/non-messaging checks; do not send messages, create real payments or exercise payout. Verify intended disabled flags and no unexpected cron invocations.
6. **Stop and recovery.** Stop on migration checksum drift, failed health, authorization leakage, ledger discrepancy, unexpected provider activity, scheduler overlap, unknown notification outcomes or failed smoke tests. Preserve logs and evidence. Roll back application code only after confirming backward compatibility; do not assume that rolling back code reverses an applied migration. Use a previously rehearsed forward fix or restore procedure chosen by the authorized database owner; never silently delete or reconstruct financial/referral history.
7. **Monitoring and activation.** Monitor error rates, webhook retry/duplicates, audit trails, background lease/DEAD/UNKNOWN counts and cursor lag. Record verification and obtain separate owner authorization before each production feature activation. Technical release readiness is not commercial programme readiness.
