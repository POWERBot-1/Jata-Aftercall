# Local test environment and Prisma client

Use Node 22.22.3 and the committed npm lockfile. In a clean checkout, run `npm ci` followed by `bash scripts/lib/prisma-generate.sh` and `npm test`. The explicit generate is necessary because the historical postinstall deliberately permits an offline generation failure. Generation reads `prisma/schema.prisma` (`prisma-client-js`, PostgreSQL) and downloads Prisma 5.22.0 engine files from the official Prisma distribution; it does not migrate or connect to a database. Where schema validation requires a URL, use a non-routable disposable placeholder for that command only, e.g. `DATABASE_URL='postgresql://validation_only:validation_only@127.0.0.1:5432/validation_only?schema=public' bash scripts/lib/prisma-generate.sh`.

`npm test` now checks that the generated client and model metadata can be loaded before starting the full suite. This detects missing generation, not schema/client drift, native engine usability, or database readiness. Always explicitly regenerate after schema changes. This preflight does not replace tests and does not silently skip them. Database tests are separately conditional and need an isolated migrated PostgreSQL instance; a no-database suite cannot certify them. Never point tests at production.

In this sandbox `npm ci --ignore-scripts` had omitted generation and the ordinary postinstall also tolerates failure. The generated `.prisma/client` was absent. An explicit native generate then failed connecting to `binaries.prisma.sh` because that host is outside sandbox egress. That explains the observed missing-client import error but does not establish that every previous failure had the same cause. `.github/workflows/full-local-suite.yml` independently performs native generation on CI and runs the full no-database suite, recording totals and failures. An unavailable local engine remains an explicit blocker, not permission to use mock binaries or label an adapter-only test as native Prisma.
